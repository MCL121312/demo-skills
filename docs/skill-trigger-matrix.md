# Skill 触发边界矩阵

用于人工回归和后续自动化测试。优先看用户的动作意图，而不是只看关键词。

| 输入信号 | 首选 Skill | 关键动作 | 不应做的事 |
| --- | --- | --- | --- |
| 群聊/工单 + “整理一下” | `implementation-intake` | 输出现场记录草稿 | 直接写 PRD 或架构方案 |
| 客户反馈 + “验收怎么测” | `implementation-intake` | 按已确认条目补验证 | 把口述直接当已复现事实 |
| 工单 + “先验证还是先开发” | `engineering-decision` | 判断验证、分析或直接执行路径 | 只按实施记录停留 |
| “接口、定时任务、共享视图怎么选” | `engineering-decision` | 比较技术方案与权衡 | 未确认就选定方案 |
| “帮我写 PRD/SRS/ADR” | `engineering-documents` | 使用对应模板生成文档 | 把未知写成已批准决策 |
| 已有 `document_contract` + 写文档 | `engineering-documents` | 严格遵守类型、状态和章节 | 用模板默认值覆盖契约 |
| “线上重复扣费/数据持续写错” | `engineering-decision` | 先止损和恢复 | 先做普通需求访谈 |
| “改一下这个 Skill 的措辞” | 无专用 Skill | 直接编辑仓库文件 | 触发业务决策或文档 Skill |
| “项目写得怎么样/代码质量如何/帮我评估这个项目” | `engineering-decision` | 先确认评估目的、阶段、目标，再给结论 | 未问目的直接给代码层面评审当结论 |
| 用户明确说“只看代码，不要问上下文”/“只做仓库静态分析” | 无专用 Skill | 检查结构、代码、测试和依赖，标记 `repository-only-assessment` | 推断组织目标或批准结论 |

## 冲突处理

- 同时出现“整理工单”和“先验证”，以研发决策动作为升级信号；先保留现场事实，再
  进入 `engineering-decision`。
- 同时出现“写 PRD”和“需求还不清楚”，先形成决策摘要或探索版文档，不生成
  `approved-baseline`。
- 同时出现事故信号和普通需求，先执行止损路径，稳定后再补普通分析。
