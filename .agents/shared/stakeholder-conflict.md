# 利益相关者冲突处理

当多方意见不一致时，Agent 的角色是整理冲突、列清选项、交给有决策权的人；
不替任何一方做选择，也不静默选边。"不静默选边"是不可覆盖的硬底线，见
`conventions.md`。

## 冲突类型与处理

### 目标冲突（一方要快，一方要稳）

1. 把冲突显式写出来，不藏着：说明各方诉求和理由。
2. 确认谁有最终决策权；决策人不在场时标“待决策”，不默认按某一方意见推进。
3. 给 2-3 个折中方案，写清各自的代价与风险（例如灰度发布兼顾速度与风险）。
4. 不替决策者拍板，把选项和后果列清楚后交还给决策人。

### 优先级冲突（各方认为不同事项最重要）

1. 请各方分别说明“为什么重要、不做的后果、最坏情况”。
2. 用统一维度评估：影响用户数、财务损失、风险、可逆性。
3. 仍不一致时升级给有决策权的人；不同意见和理由都要留痕，不只记最终结论。

### 技术方案冲突（各支持不同方案）

1. 不争论“哪个更好”，先对齐评价标准：约束是什么（团队熟悉度、性能要求、
   维护成本），每个方案在约束下的表现如何。
2. 能做小 POC 就做 POC，不纸上谈兵。
3. 做不了 POC 时记录分歧，交技术负责人拍板；决策后按决策执行，但把少数派
   意见的风险点写进 `risks`。

## 冲突记录格式

在 `information_layers.conflicts` 中记录时至少包含：当事方、主题、各方立场与
理由、解决状态、决策人。示例：

```yaml
conflicts:
  - parties: ["产品负责人", "运维负责人"]
    topic: "上线时间"
    positions:
      - party: "产品负责人"
        position: "本周上线，否则错过营销窗口"
        reasoning: "营销已排期，推迟损失约 200 万 GMV"
      - party: "运维负责人"
        position: "至少再测两周"
        reasoning: "上次类似改动导致 4 小时故障，影响 10 万用户"
    resolution_status: "待决策"
    decision_owner: "技术总监"
```

## 沟通原则

- 对事不对人：记录观点和理由，不写对人的评价。
- 冲突对相关方公开，不私下替某一方传话或定调。
- 达成一致也要留痕：记录曾有分歧及最终选择的理由。
- 僵持不下时明确指出“这需要 XX 拍板”，并暂停生成下游文档。
