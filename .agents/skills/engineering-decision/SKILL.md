# Engineering Decision

这是软件工程系列中的“决策入口”。它负责把一个模糊的工程问题逐步变成可行动
的 `decision_brief`，而不是直接把所有问题写成 PRD 或设计文档。

## 输出语言与受众文案

默认所有面向用户的内容使用简体中文。英文仅保留 YAML/JSON 字段名、固定枚举值
（如 `complex`、`L3`、`decision_brief`）、代码符号、文件路径和没有准确中文译名
的技术专名。英文术语首次出现时附中文解释，例如“复杂域（`complex`）”。除非
用户明确要求英文，否则不要输出英文标题、英文表格或英文解释段落。

区分**内部约束**与**用户可见文案**：

- 状态机、字段名、枚举值（如 `intake`、`document_contract`）只用于内部推理或
  用户明确要求的 YAML/调试输出。
- 面向用户时，只写对方需要理解的结论、事实边界和下一步问题。
- **禁止**向用户叙述“暂不做 X”“不输出 Cynefin / 复杂度 / 行为模式”“问题单状态
  保持为 `intake`”等跳过步骤的元说明。这些是 agent 的自我约束，不是用户要读的内容。
- 用户没有要求结构化结果时，不要用“问题单状态”“上下文缺口”“当前判断”等内部
  章节标题堆砌回复；用自然语言组织即可。

## 目标

1. 建立问题单。
2. 询问影响判断的组织、项目和目标上下文。
3. 将信息分层为事实、目标、约束、假设、未知、冲突、风险和决策。
4. 判断问题类型和当前 Cynefin 域。
5. 选择行为模式和用户参与度。
6. 选择下一项工程活动，并输出文档契约。

## 边界

本 Skill 负责“决定怎么做”，不负责完整“决定怎么写”。

- 用户问“应该先做还是先验证”“这个方案怎么选”：使用本 Skill。
- 用户问“帮我写 PRD/SRS/ADR/概要设计”：交给
  `engineering-documents`；若上下文不足，先生成本 Skill 的 decision brief。
- 用户只要求代码修改、翻译或格式化：不要触发本 Skill。

如果用户同时要求判断和文档，先完成决策判断，再把 `document_contract` 交给
文档工作流，不要绕过决策直接生成正式文档。

## 状态流程

```text
intake -> contextualized -> categorized -> classified -> behavior-selected
```

状态含义：

- `intake`：只有问题描述和初始目标。
- `contextualized`：组织、项目、系统、目标和约束已有基本信息。
- `categorized`：信息已按证据类型和问题类型分层。
- `classified`：已有 Cynefin 主域、置信度和证据。
- `behavior-selected`：已有行为模式、参与度、门槛和下一步。

不要为了完成状态机而重复提问。缺口只有在会改变下一步时才需要补充。

## 评估对象

必须区分以下结果：

```text
项目复杂度：项目整体需要多少协调、专业分析和控制
当前问题域：当前问题属于哪个 Cynefin 域
不确定性：我们对目标、因果关系和结果知道多少
风险：做错之后的影响和不可逆程度
```

Cynefin 判断针对“当前问题 + 当前目标 + 当前上下文”，不针对整个仓库永久分类。
项目复杂度评估规则见 `references/project-complexity.md`，结构见
`references/project-complexity-schema.yaml`。

## 工作流程

### 0. 先判断紧急性

先快速判断是否存在正在扩大的服务故障、数据丢失、越权访问、安全事件、财务损失
或用户权益持续受损。如果存在，立即进入 `stabilization`，只询问止损、恢复和安全
状态所需的最小问题；稳定后再补齐普通上下文并重新分类。

如果不存在紧急伤害，再执行目的与上下文门槛。

### 1. 目的与上下文门槛

在任何仓库扫描、复杂度评分、Cynefin 分类或行为模式选择之前，必须先确认
用户的评估目的和最小工程上下文。不能因为已经拿到代码仓库路径，就跳过这一门槛。

首轮至少确认：

1. **评估目的**：用户想支持什么决策，例如是否继续开发、是否重构、是否上线、
   是否拆分、是否补齐安全，还是只想了解项目现状。
2. **项目阶段**：探索、规划、开发、测试、试用、生产或维护。
3. **当前目标**：现阶段最重要的交付结果是什么。
4. **组织和决策者**：参与团队、主要利益相关者，以及谁有最终决策权。

如果用户没有提供这些信息，先提问，不要开始复杂度分析。默认最多提出四个问题，
可以合并成一个简短问卷：

> 在分析仓库前，我需要确认四件事：你希望这个评估支持什么决策？项目目前处于
> 什么阶段？当前最重要的目标是什么？有哪些团队参与，谁拥有最终决策权？

以下情况可以减少提问：

- 用户已经明确给出了评估目的、阶段、目标和决策者。
- 用户明确要求“只做仓库静态分析”，此时必须把输出标记为
  `repository-only-assessment`，不得推断组织、项目目标或最终推进策略。
- 当前是紧急事故，先进入 `stabilization`，但仍需在稳定后补齐上下文。

仓库事实不能替代组织和目标上下文。读取代码只能回答“当前实现是什么”，不能
回答“项目为什么这样做”“现在应该优先做什么”或“谁可以批准改变”。

如果门槛尚未通过：

**内部约束**（遵守但不写入用户可见回复）：

- 问题单状态保持为 `intake`。
- 不得给出项目复杂度等级、Cynefin 域、行为模式或最终优先级结论。

**面向用户只写**：

1. 用自然语言重述已知问题（不要贴内部字段名）。
2. 说明还缺哪些信息才能继续判断（用业务语言：目的、阶段、目标、谁拍板）。
3. 最多四个门槛问题。

错误示范：`问题单状态保持为 intake，暂不做复杂度、Cynefin 域或推进策略判断。`

正确示范：先概括需求，再直接问四件还缺的事，不要解释自己跳过了哪些分析步骤。

### 2. 建立问题单

先用一句话重述问题，建立最小问题单。记录：

- 问题或机会是什么。
- 谁提出、谁受影响。
- 期望结果是什么。
- 当前紧迫性、风险和可逆性是否已知。
- 用户期望建议、方案、文档还是执行。

问题单字段参考：`references/issue-schema.yaml`。

### 3. 采集上下文

通过目的门槛后，只询问仍会影响决策的上下文，优先顺序如下：

1. 当前阶段和目标。
2. 受影响的用户、系统和团队。
3. 谁拥有决策权，谁需要被咨询。
4. 项目规模、技术复杂度和依赖。
5. 成功指标、期限和约束。
6. 风险、影响范围、可逆性和已有证据。

可以读取仓库、现有文档和决策记录，但必须区分“当前实现行为”和“期望行为”。
仓库扫描是证据采集步骤，不是目的确认步骤。
项目复杂度只是上下文，不等于当前问题的 Cynefin 域。

如果评估目的要求了解项目整体复杂度，使用八个维度进行 `0-4` 评分：业务领域、
技术、集成、组织、不确定性、变化、运行和风险。必须记录证据、置信度和主要来源；
不得只依据文件数量、代码量或团队人数评分。

项目复杂度评分完成后，单独判断当前问题域。即使项目整体复杂度高，当前一个明确
且可逆的字段变更仍可能属于 `clear`；小项目中的未知用户问题也可能属于 `complex`。

### 4. 信息分层

把输入按 `facts`、`goals`、`constraints`、`assumptions`、`unknowns`、
`conflicts`、`risks`、`decisions` 八层归类，每层的定义、示例和证据要求见
`references/information-layers.md`。

不要把推断写入 `facts`，不要把建议写入 `decisions`。

### 5. Cynefin 判断

只有在上下文和信息分层达到足够程度后再判断。详细规则见
`references/cynefin-domains.md`。

紧急伤害判断已在步骤 0 完成；若在此阶段新发现正在扩大的伤害，同样优先进入
`stabilization`。这表示行为优先级，不表示已经理解完整原因。

条件映射：

| 条件 | 主工作方式 | 典型域 |
| --- | --- | --- |
| 目标、规则、输入和验收标准清晰，因果关系稳定 | 直接推进 | `clear` |
| 有可知答案，但需要专家比较或技术权衡 | 专家分析 | `complicated` |
| 需求、用户行为、采用结果或因果关系未验证 | 迭代探索 | `complex` |
| 存在事故、主动伤害、数据丢失或安全事件 | 稳定化 | `chaotic` |
| 信息不足或存在关键冲突，无法判断 | 先澄清 | `confused` |

输出主域、置信度、证据、备选域和重新分类条件。不要展示隐藏推理。

置信度限制行为：

| 置信度 | 允许输出和行动 |
| --- | --- |
| `high` | 可以给出明确路径和候选文档，但仍需遵守高风险确认门槛 |
| `medium` | 可以给出建议，必须标记假设、替代判断和重新分类条件 |
| `low` | 只输出问题单、未知项、上下文缺口和澄清问题，不给正式架构结论、最终优先级或批准基线 |

### 6. 选择行为模式

可选模式为 `direct-execution`、`expert-analysis`、`iterative-discovery`、
`stabilization`、`clarification`、`review-and-alignment`，各自的适用条件、
产出要求和退出信号见 `references/behavior-modes.md`。

行为模式不只由 Cynefin 决定，还要考虑风险、紧迫性、影响、可逆性和用户偏好。

### 7. 调整用户参与度

使用 `L0` 至 `L4`，等级定义、默认映射和提高参与度的条件见
`references/engagement-policy.md`。核心原则：`clear` 偏低参与度，`chaotic`
和 `confused` 偏高参与度；不可逆、高风险、跨团队、安全或利益冲突的决策必须
提高参与度，且用户要求“全自动”不能覆盖高影响确认门槛。

### 8. 输出 decision brief

结构以 `references/decision-schema.yaml` 为准，不在此处重述全部字段。填充时确保
上下文摘要、信息分层、分类判断、行为与参与度、允许行动与确认门槛、下一步、
`document_contract` 和待回答问题都有依据。

内部始终构造结构化 `decision_brief`，但默认不把完整 YAML 展示给用户。默认将其
渲染为简体中文决策摘要；只有用户明确要求 YAML/JSON、需要调试、保存文件或跨
Skill 传递时，才展示或保存结构化内容。案例参考见 `EXAMPLES.md`，只在遇到边界
不清或需要具体示例时按需读取，不要每次默认加载全文。

`document_contract` 是和 `engineering-documents` 的边界，只描述文档类型、状态、
目的和结构，不承载完整文档内容。

## 询问策略

目的与上下文门槛的规则（含四个门槛问题上限、`repository-only-assessment` 和
门槛未通过时的输出限制）以“工作流程 1”为准，不在此重复。

- 信息充分时直接输出 decision brief，不要为了形式再提问。
- 普通信息不足时，单轮最多提出三个高影响问题；紧急事故只询问立即止损所需的
  问题。
- `L3` 或 `L4` 时，先确认目标、边界、决策权和关键假设。
- 明确要求“先给我问题单”时，只生成问题单和缺口，不提前进行完整分类。
- 发生线上事故、主动伤害或数据风险时，先稳定化，不进行普通需求访谈。

## 输出协议

目的门槛尚未通过时：不要套用下面的完整摘要结构；按“工作流程 1”的面向用户
三项输出，并遵守受众文案规则。

门槛已通过、且用户不是只要结构化 YAML 时，将内部 `decision_brief` 渲染为中文
决策摘要，覆盖这些内容（可用自然语言，不必机械套标题）：

1. **问题**：当前问题、目标、影响范围。
2. **已知与未知**：事实、缺口、冲突（需要时才提）。
3. **当前判断**：问题类型、Cynefin 域、置信度和证据。
4. **怎么推进**：行为模式、参与度、允许行动和确认门槛。
5. **下一步**：具体动作；文档契约仅在需要下游文档时说明用途，不要甩内部字段名。
6. **需要用户决定的问题**：数量上限见“询问策略”。

不要把 `engineering-documents` 应该完成的整篇文档塞进本次输出，除非用户明确
要求临时内联生成。

内部字段可以使用英文固定值，但面向用户的默认结果必须使用中文。例如将
`cynefin_domain: complicated` 渲染为“当前属于繁杂域（`complicated`）”。只有在
判断已经做出、且对用户有用时，才解释域或行为模式；不要为了“流程完整”而提前
抛术语。

## 完成前检查

- 已区分项目复杂度与当前问题域。
- 已在仓库分析和复杂度判断前确认评估目的、项目阶段、当前目标和决策权。
- 面向用户的内容默认使用简体中文，英文仅用于固定字段、代码和必要专名。
- 用户可见回复未暴露内部状态机、未叙述“暂不做某某分析”。
- 未将假设、推断或建议写成事实或已确认决策。
- Cynefin 判断有证据、置信度和重新分类条件。
- 行为模式考虑了风险、可逆性和影响范围。
- 文档契约与当前确定性匹配。
- 高风险或不可逆行动具有明确确认门槛。
- 下一步具体、可执行且不超出当前证据。
