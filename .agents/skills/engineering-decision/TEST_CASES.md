# engineering-decision 测试用例

本文件仅供维护者人工回归测试使用，agent 执行 Skill 时无需读取。

这些用例用于人工验证语义触发、边界和工作方式选择。通过标准不是逐字输出，
而是触发或避开 Skill，并选择合理的下一个动作。

## 前置门槛

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 只提供一个仓库路径并问“项目复杂度如何” | 用自然语言重述缺口并询问评估目的、阶段、当前目标、决策者；内部保持 `intake` | 输出复杂度等级、Cynefin 域、行为模式、最终优先级；向用户说“状态为 intake / 暂不做某某判断” |
| 用户说“只做仓库静态分析，不需要组织背景” | 输出标记 `repository-only-assessment`；可读取仓库 | 推断组织目标、决策权或最终推进策略 |
| 用户明确说明“线上正在数据丢失” | 进入 `stabilization`；只问止损/恢复最小问题 | 普通需求访谈、长期架构设计 |
| 用户已说明评估用于上线决策、项目处于测试阶段、目标是完成首版上线、技术和产品负责人共同决策 | 可通过目的门槛；继续采集事实与复杂度评估 | 为走流程再重复问已给出的四项门槛 |

## 输出语言与受众文案

| 输入 | 预期行为 |
| --- | --- |
| 用户使用中文提问且没有指定输出语言 | 所有解释、问题和分析使用简体中文；固定枚举值可保留英文 |
| 用户说“请用英文输出” | 可以输出英文，并保持结构化字段稳定 |
| 分析中出现 `complex`、`L3` 或 `decision_brief` | 首次出现时附中文解释，例如“复杂域（`complex`）” |
| 目的门槛未通过，只能先提问 | 只重述已知问题并提问；禁止写“问题单状态 / 暂不做复杂度或 Cynefin 判断”等过程旁白 |

## 复杂度与分类边界

| 情况 | 预期行为 |
| --- | --- |
| 大型项目中的明确字段修改 | 项目复杂度可以高，但当前问题仍可判断为 `clear` |
| 小型项目但不知道用户需要什么 | 项目规模可以低，但当前问题可以是 `complex` |
| 技术很难但目标、协议和验收标准明确 | 倾向 `complicated`，不因技术难直接判为 `complex` |
| 只提供仓库路径要求评估 | 未通过目的门槛前不评分、不分类 |
| 仓库静态分析模式 | 标记 `repository-only-assessment`，不推断组织和最终行为 |
| 存在正在扩大的数据损失或安全事件 | 优先 `stabilization`，先止损，稳定后再补普通上下文 |
| 分类置信度为 `low` | 只输出问题单、未知项和澄清问题，不输出正式架构结论 |
| 关键复杂度维度为 `unknown` | 不计算总体平均分，保留缺口并标记总体复杂度为 `unknown` 或 `provisional` |

## 短句中文触发（易漏触发，优先回归）

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 这是啥需求 | 读取并执行本 Skill；用自然语言重述问题并走目的门槛；内部可停在 `intake` | 把用户话当成对 Agent 上一段回答的元澄清；直接给完整 PRD/架构；向用户曝光状态机旁白 |
| 帮我看看这个需求 | 同上，先分层事实/假设/未知 | 未确认目的就输出复杂度或最终优先级 |
| 怎么推进 | 输出行为模式建议或先问门槛问题 | 直接开写代码或正式基线文档 |
| 先调研还是直接开发 | 完成 Cynefin/行为判断或先补关键上下文 | 只给空泛建议、不走 decision brief 流程 |

## 应触发

| 输入 | 预期行为模式 | 预期域 | 必须 | 禁止 |
| --- | --- | --- | --- | --- |
| 帮我梳理这个想法并输出 PRD | `clarification` 或 `iterative-discovery` | 通常 `confused` / `complex` | 先决策再文档契约；未知标为假设 | 直接写成 `approved-baseline` PRD |
| 这个需求应该先调研还是直接开发 | 由证据决定，先完成 Cynefin 判断 | 根据证据判断 | 输出域、置信度、证据、下一步 | 在证据不足时给最终路径 |
| 根据 PRD 生成概要设计并检查是否缺信息 | `expert-analysis` 或 `direct-execution` | 通常 `complicated` 或 `clear` | 列出信息缺口；可给 `document_contract` | 把缺口静默填成虚构架构 |
| 检查 PRD、SRS 和 UX 是否互相矛盾 | `review-and-alignment` | 不预设 | 记录冲突并交给授权人 | 自行挑一边当最终决策 |
| 用户不知道 AI 助手最需要什么功能，先帮我设计验证方式 | `iterative-discovery` | `complex` | 假设 + 验证方式 + 成功指标 | 跳过验证直接详细设计 |
| 线上发生重复扣款，先帮我组织止损和恢复 | `stabilization` | `chaotic` | 止损/恢复步骤与确认门槛 | 先写长期 PRD 或架构 |

## 不应主动触发

| 输入 | 原因 |
| --- | --- |
| 把函数名从 `foo` 改成 `bar` | 代码修改，不是需求工作流 |
| 把这段英文翻译成中文 | 翻译任务 |
| 给这段 Markdown 加目录 | 格式化任务 |
| 按这份完整 API 规格生成接口代码 | 机械实现，需求已明确 |
| 这个 skill 还有改进空间吗 / 修一下校验脚本 | 维护本仓库的元任务，不是业务工程决策 |
| README 受众怎么写 | 文档文案维护，不是用户需求 intake |

## 边界验证

- “帮我直接把这段需求改写成 PRD”：直接生成草稿，不强制完整访谈。
- “这个系统技术上很难，但协议和目标都已确定”：倾向 `complicated`，不因
  为“难”直接判为 `complex`。
- “需求混乱但没有线上事故”：倾向 `confused`，不判为 `chaotic`。
- “用户要求全自动发布数据库迁移”：因不可逆和高风险提高参与度并要求确认。
- “没有 decision brief，直接要求生成 SRS”：可以不阻塞，但必须标记未知和假设，不能生成正式确定性结论。
- “置信度为 `low` 但要求 `approved-baseline`”：拒绝提升状态，保持 `exploratory-draft` 并说明缺口。
- “线上事故期间要求生成长期架构设计”：先执行 `stabilization`，长期设计延后到系统稳定后。

## 快速通道

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 把 phone 字段改名为 mobile，要注意什么 | 走快速通道直接给操作建议，并确认关键前提（如表是否只被本服务读） | 强制四项门槛提问；生成完整 decision brief |
| Go 日志库选 zap 还是 logrus？要结构化、性能敏感 | 快速比较并推荐，注明未说明的约束可能改变结论 | 升级为完整评估或访谈 |
| 用户表加身份证号字段，前端传上来直接存 | 退出快速通道：涉敏感个人信息合规与安全，走完整流程并提高参与度 | 当作低风险小改动直接给方案 |
| 线上事故仍在扩散 | 进入 `stabilization`，最小提问先止损 | 用快速通道处理事故 |

## 有效期与重评

| 输入 | 预期行为 |
| --- | --- |
| 用户带来一个月前的 decision brief 和偏差显著的上线数据 | 触发重评：读取旧简报、标记 `superseded_by`，证伪假设转入 `risks` |
| 用户明确说“这个先不做了” | 决策标 `deferred` 并记录原因，不删除记录 |
| 事故已稳定 | 从 `chaotic` 重新分类，退出 `stabilization`，补齐普通上下文 |
