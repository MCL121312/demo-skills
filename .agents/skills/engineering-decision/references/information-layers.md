# 信息分层

## 分层规则

| 层 | 含义 | 示例 |
| --- | --- | --- |
| `facts` | 已提供或验证的信息 | 当前订单服务使用 MySQL |
| `goals` | 希望达成的结果 | 查询失败率低于 0.5% |
| `constraints` | 不能随意改变的条件 | 不能更换数据库 |
| `assumptions` | 暂时采用但未验证的判断 | 用户更需要精确搜索 |
| `unknowns` | 当前不知道的信息 | 主要用户是谁 |
| `conflicts` | 目标、事实或利益相关者之间的冲突 | 产品要快，安全团队要求完整审计 |
| `risks` | 可能的负面结果和处理方式 | 迁移可能导致数据不一致 |
| `decisions` | 已由授权者确认的选择 | 第一阶段只支持精确搜索 |

## 证据要求

`decision-schema.yaml` 中每个层用裸列表存储条目（`facts: []`）。记录内容时：

- 可在条目文字中内联注明来源、置信度或负责人，例如：
  `"当前订单服务使用 MySQL（来源：架构文档，置信度：高）"`。
- 不要把推断或候选方案直接写成列表项，而应放入 `assumptions` 或 `unknowns`。
- 建议和候选方案不能写入 `decisions`，除非有授权者和确认状态。
- 代码中的现有行为可以作为事实，但不能自动变成期望行为。
