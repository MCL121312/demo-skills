# implementation-intake 测试用例

本文件仅供维护者人工回归测试使用，agent 执行 Skill 时无需读取。

通过标准不是逐字输出，而是触发或避开 Skill，并在条目拆分、角色归属、冲突判定
和去重上做出正确选择。

## 角色与提出人（本轮新增，优先回归）

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 「Fun 说她改不了血压」 | 角色写「录入人员」，提出人写「Fun」，两项都出现 | 角色写成「Fun」；提出人只藏在证据原话里不单独标 |
| 一段群聊里 Fun 提 A、老王提 B | 每条条目各自带自己的提出人 | 记录级只写一个提出人；把两人合并成「群里若干人」 |
| 提出人与操作者是同一人（前台自己报自己的问题） | 两项可写同一值，仍分别标注 | 因为相同就省略提出人 |
| 条目已有七列 | 提出人与证据写在表格下方的 `条目N · 提出人 X（时间）：「原话」` 行 | 为提出人新增第八列表格 |

## 冲突判定（本轮新增，优先回归）

| 输入 | 是否进冲突区 | 说明 |
| --- | --- | --- |
| Fun：「最近很多地方都锁住了吗」；Sincerity：「没有锁」 | **是** | 两句互斥断言，指向同一事实 |
| i 说「预约 vs 激活短信」；Liujg 问「检前 vs 导检要留哪边」 | **否** | Liujg 在提问，未否定任何断言；叫法差异归未知/待确认 |
| 客户要求本周上线；实施说本周排不开 | **是** | 对同一约束给出互斥断言 |
| 没人提过某页面叫什么 | **否** | 信息缺失，归未知 |
| 群里有人问「这是不是缓存问题」，无人回答 | **否** | 未回答的提问，归未知或待确认 |
| 全场无互斥断言 | **否** | 整个冲突区省略，不留空标题 |

## 证据等级与复现（本轮新增，优先回归）

| 输入 | 预期行为 |
| --- | --- |
| 「客户说改不了，我没试过」 | 等级 `客户口述`、`未复现`；不得标已确认或交接 |
| 「我自己点了三次都复现了」 | 等级 `亲见`、`已复现`；可正常流转 |
| 「应该是缓存吧」 | 等级 `推测`；不得标已确认 |
| 「试了半天重现不出来」 | `无法复现`；可关闭但要记录试过的步骤，不许静默关掉 |
| 客户语气非常肯定但无人验证 | 仍是 `客户口述`，不因语气升级 |
| 未复现的缺陷 | 待确认里必须有一个复现问题（谁、什么条件、哪个单号） |
| 字段顺序不合理这类无故障条目 | 复现填 `不适用`，现象后缀只写等级 |
| 未复现却被要求开研发工单 | 拒绝直接交接；或在去向里注明按无法复现线索移交 |
| 现象格已带后缀 | 表格仍为六列，未因此新增列 |

## 标识、状态与去向（本轮新增，优先回归）

| 情况 | 预期行为 |
| --- | --- |
| 首轮输出一份新记录 | 标题行有 `IN-YYYYMMDD-NN`，条目用 `#1`、`#2` |
| 用户说「条目2 不要了」 | 该条标 `已关闭`；新条目取 `#3`，不复用 2 |
| 一条已拍板、另一条还在澄清 | 状态逐条流转，不整份记录一起翻 |
| 首轮全部为 `待确认` | 状态整项不渲染，输出不因新字段变重 |
| 条目开了研发工单 | 状态 `已交接` 且回填工单号 |
| 只是口头说「这个要研发」 | 不改状态，不算交接 |
| 新增了标识、状态、去向三个字段 | 表格仍不超过六列 |

## 去重

| 情况 | 预期行为 |
| --- | --- |
| 某项不确定已写成待确认问题 | 未知区和冲突区都不再重复同一句 |
| 冲突衍生出一个需要人拍板的问题 | 冲突区记互斥断言，待确认区记问题，两者措辞不重复 |
| 未知区能列的都已在三个待确认问题里 | 未知区留真正没问的缺口，或整项省略 |

## 拆条

| 输入 | 预期 |
| --- | --- |
| 一句话里既报故障又提顺序优化 | 拆两条，故障为主、优化为次 |
| 有现象无诉求 | 建条，诉求写「待澄清」，追问期望结果 |
| 有诉求无现象 | 建条，现象写「无故障现象，属体验/顺序/配置问题」 |
| 同一诉求被三个人重复提 | 一条条目，提出人可并列，不拆成三条 |

## 模块与证据

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 对话没提页面名 | 模块写「待确认」 | 编造产品菜单名 |
| 只有一句原话 | 证据引用原话并署发言人 | 把他人发言改写成提出人所说 |

## 同步类诉求

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 「去掉重复填写，但要能同步到系统」 | 验证含同步检查；未证实标「待证实」 | 承诺「删了也会进系统」；首轮给保留/去掉方案 |
| 库里两套表且无同步任务 | 出条目并标「需研发」 | 展开双写/CDC 选型对比 |

## 应触发

| 输入 | 预期 |
| --- | --- |
| 粘贴企微群聊并说「整理一下」 | 出现场记录草稿，状态待确认 |
| 「这是啥需求」+ 一段客户反馈 | 出条目四元组；整段可原样转发，不含内部流程术语或状态旁白 |
| 「帮我看看这个工单」 | 同上；缺模块时写「待确认」 |
| 「验收怎么测」 | 按已确认条目补验证步骤 |

## 不应主动触发

| 输入 | 原因 |
| --- | --- |
| 同步方案在接口、定时任务、共享视图里怎么选 | 研发级选型，转 `engineering-decision` |
| 先验证还是先开发 | 转 `engineering-decision` |
| 按已批准澄清写 SRS | 转 `engineering-documents` |
| 把这段话翻译成英文 | 与本系列无关 |
| 改一下这个 skill 的措辞 | 维护本仓库的元任务 |

## 边界验证

- 用户只说「整理现场」：停在现场记录，不串文档工作流。
- 用户没要求落盘：不写 markdown 文件。
- 用户没点名要用户故事：不输出故事或 UML 正文。
- 存在正在扩大的错误写入或重复扣费：先给止损提示，再回来整理。
- 人未确认拆条前：不推进配置变更，也不做研发承诺。
