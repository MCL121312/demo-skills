# implementation-intake 测试用例

本文件仅供维护者人工回归测试使用，agent 执行 Skill 时无需读取。

通过标准不是逐字输出，而是 Agent 是否做出正确的思考、提问和判断。

## 项目认知建立

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 项目有清晰的模块结构 | Agent 扫描后能基于模块名提问 | 问"请提供模块名称"这种泛泛的问题 |
| 项目结构不清晰或无法扫描 | Agent 说明"我对项目结构了解有限" | 假装知道或编造模块名 |
| 最近有相关 commit | Agent 能关联到当前问题 | 忽略最近的变更 |

## 感知阶段

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 群聊里有多件事 | Agent 先说出"我看到几件事"，让实施人员纠正 | 直接输出完整表格 |
| 一件事被多人重复提 | Agent 识别为一条，不拆成多条 | 把同一件事拆成多条 |
| 问题与诉求并存 | Agent 识别出要拆条 | 揉成一句模糊诉求 |

## 评估与提问

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 模块名未出现 | Agent 基于项目认知给候选答案让实施人员选 | 问"请提供模块名称" |
| 证据等级不明 | Agent 问"是你自己看到的还是客户告诉你的" | 问"证据等级是什么" |
| 复现状态不明（缺陷类） | Agent 问"这个情况能稳定重现吗" | 跳过复现问题直接标已确认 |
| 实施人员说"不知道" | Agent 标"待确认"，不反复追问 | 逼迫实施人员回答 |
| 多条事项并存 | Agent 逐条收敛，先搞定一条再聊下一条 | 同时推进多条条目的补全 |

## 沟通原则

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 信息不足需要提问 | Agent 用大白话说明缺什么 | 暴露框架术语（Cynefin、信息分层、状态机） |
| 需要纠正理解 | Agent 在对话中让实施人员纠正 | 最后输出完整记录让人审 |
| 实施人员问"这是什么域" | Agent 用业务语言解释，不抛术语 | 说"这是 complex 域"而不解释含义 |

## 角色与提出人

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 「Fun 说她改不了血压」 | 角色写「录入人员」，提出人写「Fun」 | 角色写成「Fun」 |
| 一段群聊里 Fun 提 A、老王提 B | 每条条目各自带自己的提出人 | 记录级只写一个提出人 |
| 提出人与操作者是同一人 | 两项可写同一值，仍分别标注 | 因为相同就省略提出人 |

## 冲突判定

| 输入 | 是否进冲突区 | 说明 |
| --- | --- | --- |
| Fun：「最近很多地方都锁住了吗」；Sincerity：「没有锁」 | **是** | 两句互斥断言，指向同一事实 |
| i 说「预约 vs 激活短信」；Liujg 问「检前 vs 导检要留哪边」 | **否** | Liujg 在提问，未否定任何断言 |
| 客户要求本周上线；实施说本周排不开 | **是** | 对同一约束给出互斥断言 |
| 没人提过某页面叫什么 | **否** | 信息缺失，归未知 |
| 全场无互斥断言 | **否** | 整个冲突区省略 |

## 证据等级与复现

| 输入 | 预期行为 |
| --- | --- |
| 「客户说改不了，我没试过」 | 等级 `客户口述`、`未复现`；不得标已确认或交接 |
| 「我自己点了三次都复现了」 | 等级 `亲见`、`已复现`；可正常流转 |
| 「应该是缓存吧」 | 等级 `推测`；不得标已确认 |
| 「试了半天重现不出来」 | `无法复现`；可关闭但要记录试过的步骤 |
| 客户语气非常肯定但无人验证 | 仍是 `客户口述`，不因语气升级 |
| 未复现的缺陷 | 待确认里必须有一个复现问题 |
| 未复现却被要求开研发工单 | 拒绝直接交接 |

## 域判断与分流

| 输入 | 预期域判断 | 去向 |
| --- | --- | --- |
| 类型为流程配置且模块明确 | `clear` 或 `complicated` | 配置侧处理 |
| 类型为缺陷且需改接口/库表 | `complicated` | 标"需研发" |
| 用户要先验证/选型 | 由 `engineering-decision` 判断 | 转 `engineering-decision` |
| 需求未验证、依赖用户行为 | `complex` | 建议实验或 MVP |
| 信息不足无法判断 | `confused` | 继续提问 |

## 拆条

| 输入 | 预期 |
| --- | --- |
| 一句话里既报故障又提顺序优化 | 拆两条，故障为主、优化为次 |
| 有现象无诉求 | 建条，诉求写「待澄清」，追问期望结果 |
| 有诉求无现象 | 建条，现象写「无故障现象，属体验/顺序/配置问题」 |
| 同一诉求被三个人重复提 | 一条条目，提出人可并列，不拆成三条 |

## 模块与证据

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 对话没提页面名 | 模块写「待确认」 | 编造产品菜单名 |
| 只有一句原话 | 证据引用原话并署发言人 | 把他人发言改写成提出人所说 |

## 同步类诉求

| 输入 | 必须 | 禁止 |
| --- | --- | --- |
| 「去掉重复填写，但要能同步到系统」 | 验证含同步检查；未证实标「待证实」 | 承诺「删了也会进系统」 |
| 库里两套表且无同步任务 | 出条目并标「需研发」 | 展开双写/CDC 选型对比 |

## 应触发

| 输入 | 预期 |
| --- | --- |
| 粘贴企微群聊并说「整理一下」 | 进入对话式补全，先感知再提问 |
| 「这是啥需求」+ 一段客户反馈 | 出条目四元组；用大白话沟通 |
| 「帮我看看这个工单」 | 同上；缺模块时基于项目认知提问 |
| 「验收怎么测」 | 按已确认条目补验证步骤 |

## 不应主动触发

| 输入 | 原因 |
| --- | --- |
| 同步方案在接口、定时任务、共享视图里怎么选 | 研发级选型，转 `engineering-decision` |
| 先验证还是先开发 | 转 `engineering-decision` |
| 按已批准澄清写 SRS | 转 `engineering-documents` |
| 把这段话翻译成英文 | 与本系列无关 |
| 改一下这个 skill 的措辞 | 维护本仓库的元任务 |

## 边界验证

- 用户只说「整理现场」：停在现场记录，不串文档工作流。
- 用户没要求落盘：不写 markdown 文件。
- 用户没点名要用户故事：不输出故事或 UML 正文。
- 存在正在扩大的错误写入或重复扣费：先给止损提示，再回来整理。
- 人未确认拆条前：不推进配置变更，也不做研发承诺。
- Agent 不应该一次性输出完整记录，而应该对话式逐条收敛。
