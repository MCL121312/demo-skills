# 现场记录案例

说明 `implementation-intake` 的对话式整理方式。重点展示 Agent 怎么思考、怎么提问、
怎么收敛，而不是最终输出长什么样。

## 案例一：血压群聊（主路径）

### 用户输入

> Fun：顾客录错了血压，我修改不了；把舒张压和收缩压换一下位置好一点。
> 许宁宁：这个页面这里是先舒张压再收缩压，确实改一下会好一点。
> Fun：我改了两次都没成功。
> 许宁宁：我帮你改了……不行，刷新就没了，以前可以……又可以了。
> Fun：最近很多修改的地方都锁住了，是吗？
> Sincerity：没有锁，我们排查一下问题。

### Agent 的感知阶段

Agent 快速识别出两件事：

1. 血压数据修改异常（改不了、刷新丢失）—— 缺陷，优先级高
2. 字段顺序想从"舒张压/收缩压"改成"收缩压/舒张压" —— 体验优化，优先级低

还注意到一个冲突信号：Fun 说"很多地方锁住了"，Sincerity 说"没有锁"。

Agent 用大白话告诉实施人员：

> "这段对话里我看到两件事：一个是血压数据改不了、刷新会丢；另一个是字段顺序
> 想换一下。还有个地方说法不一致——Fun 觉得很多地方锁住了，Sincerity 说没有。
> 我先问你血压改不了这个问题——"

### Agent 的评估与提问

**条目1（血压修改）评估：**
- 角色：录入人员 ✓（从"顾客录错了"推断）
- 模块：血压编辑页面 ✗（对话没提具体页面名）
- 现象：修改后刷新数值恢复 ✓（许宁宁亲见）
- 诉求：录错后能改成功且持久 ✓
- 证据等级：许宁宁亲见 ✓
- 复现状态：未复现（"又可以了"说明没稳定重现）✗

Agent 基于项目认知提问（假设已扫描过项目，知道有"个人健康监测"和"体检报告"两个模块都有血压功能）：

> "许宁宁说他帮你改了但刷新就没了，后来又可以了——这个情况是只有这个病人
> 出现过，还是其他人也有？另外这个血压页面是个人健康监测里的还是体检报告里的？"

**条目2（字段顺序）评估：**
- 角色：录入人员 ✓
- 模块：血压编辑页面 ✗（同条目1，待确认）
- 现象：先舒张压后收缩压，易录反 ✓（许宁宁亲见）
- 诉求：顺序改为收缩压→舒张压 ✓
- 证据等级：亲见 ✓
- 复现状态：不适用（非缺陷）✓

这条信息已经足够，Agent 可以直接确认：

> "字段顺序这个我理解了：现在表单里先舒张压后收缩压，和列标题的顺序反了，
> 容易录反。你想改成收缩压在前。对吗？"

### 收敛与域判断

**条目1** 确认后，Agent 做域判断：
- 现象存在但复现不稳定 → 需要排查根因
- 结合项目认知（如果最近改过权限或缓存逻辑）→ 可能是 `complicated`（有可知答案，需要专家排查）
- 去向：标"需研发"

**条目2** 确认后：
- 明确的体验优化，因果关系清晰 → `clear` 或 `complicated`（取决于改字段顺序是否涉及后端存储逻辑）
- 如果 Agent 知道前端表单顺序和后端存储是独立的 → `clear`，配置侧可处理
- 如果不确定 → `complicated`，需要研发评估

### 不应做的事

- 不要首轮写"查缓存/接口"当诉求或方案。
- 不要把两条揉成"血压相关都改一下"。
- 不要把角色写成"Fun"；Fun 是提出人，角色是录入人员。
- 不要因为 Fun 说得肯定就把条目1 标成亲见。
- 不要输出保留/去掉/同步变更清单。
- 不要一次性输出完整表格让人审，要对话式逐条确认。
- 不要问"请提供模块名称"，要基于项目认知问精准问题。

## 案例二：重复填写（冲突反例）

### 用户输入

> 这是在公众号预约入职时需要填写的信息，下面这个是激活后收到短信需要填写的，
> 上面很多信息都重复填写……填写一遍就够了、如果删除一些重复的请确认填写一遍
> 是否会同步到系统……是客户在预约时已经填写过这些信息了，然后客户到了体检科
> 激活缴费后收到短信又需要填写一遍。只需要填写一次就够了，但是要确保填写的
> 可以同步到系统。

以上由客户方 i 提出。另有实施侧 Liujg 追问：检前与导检会分别弹窗，要保留哪边去掉另一边吗？

### Agent 的思考

**感知：** 一件事——预约和激活短信两次填写重复，希望只填一次且数据进系统。

**评估：**
- 角色：入职体检客户 ✓
- 模块：预约填写/激活短信填写 ✗（待确认是否即检前/导检）
- 现象：预约已填后，激活缴费短信再次要求填写同类必填项 ✓（客户口述）
- 诉求：只填一次，且数据进入系统 ✓
- 证据等级：客户口述（实施方没有自己走一遍两个入口）
- 复现状态：不适用（非缺陷）

**关键判断：** Liujg 的提问不是冲突——他在问"留哪边"，没有否定 i 的任何断言。
"预约/激活短信"与"检前/导检"只是叫法不同，属于待确认，不进冲突区。

**提问：**
> "我理解是一件事：预约时填过的信息，激活后短信又让填一遍，希望只填一次且
> 数据能进系统。有两个问题：1. 主录入入口以哪次为准？检前/导检和预约/短信是
> 同一对吗？2. 现网是否已有从主录入到目标系统的同步？"

**域判断：**
- 如果同步已存在 → `clear`，配置侧可处理
- 如果同步不存在且需要开发 → `complicated`，标"需研发"
- 如果不确定用户行为（是否所有入职客户都遇到）→ `complex`，建议先验证影响范围

### 不应做的事

- 不要把入口叫法差异写进冲突区。
- 不要直接写 PRD/SRS。
- 不要在未证实同步时承诺"删了也会进系统"。
- 不要擅自选定"留检前去导检"。

## 案例三：规则已清，补验证即可

### 用户输入

> 业务已确认：入职预约表为唯一填写入口；激活短信里的健康史、紧急联系人两段
> 改为只读展示预约数据；HIS 已通过预约单号拉取。请整理验收点，我们周五改配置。

### Agent 的处理

这条信息已经足够完整：
- 决策已确认（预约表为唯一入口）
- 方案明确（激活短信改为只读展示）
- 依赖已确认（HIS 已拉取）

Agent 不需要再提问，直接补验证步骤：

> "明白了。验收点应该是：1. 预约表填写后，激活短信里的健康史和紧急联系人
> 显示为只读，数据与预约一致；2. HIS 能通过预约单号拉到数据。周五配置变更
> 出来后告诉我变更单号，我更新记录。"

状态直接标 `已确认`，待确认可空。不升级到 `engineering-decision`。

## 案例四：实际要改接口才能同步

### 用户输入

> 想去掉导检重复表，但库里预约和导检是两套表，中间没有同步任务，以前都靠客户再填。

### Agent 的思考

**感知：** 一件事——去掉导检重复填写，但需要数据同步。

**评估：**
- "库里是两套表、中间没有同步任务"——如果无人查过库，等级是客户口述，不能当成事实

**提问：**
> "你说库里预约和导检是两套表、没有同步任务——这个是你查过库确认的，还是
> 听别人说的？如果是查过的，能告诉我大概是什么数据库、哪两张表吗？"

**域判断：**
- 如果确认无同步 → 需要开发同步机制 → `complicated`，标"需研发"
- Agent 不展开双写/CDC 选型，那是 `engineering-decision` 的事

## 案例五：误路由

| 用户说 | 正确技能 |
| --- | --- |
| 这段群聊整理成现场记录 / 有啥现象和诉求 | `implementation-intake` |
| 同步方案在接口、定时任务、共享视图里怎么选 | `engineering-decision` |
| 按已批准澄清写 SRS | `engineering-documents` |
| 把这段话翻译成英文 | 不触发本系列技能 |
