# Implementation Intake

面向**实施人员**的信息结构化引擎：通过对话把现场噪声（群聊、工单、口述）收敛成
结构化的现场记录条目。Agent 负责思考——结合项目上下文评估信息完整度、识别缺口、
做 Cynefin 域判断；实施人员负责提供信号——描述现场看到和听到的。

与 `engineering-decision` 并行。实施链路默认走本 Skill；只有实施方明确要求做研发级
判断（先验证还是先做、架构权衡、事故止损）时，再交给 `engineering-decision`。

核心概念见 `../../shared/cynefin.md`、`../../shared/information-layers.md`、
`../../shared/engagement-and-behavior.md`；基线覆盖关系见
`../../shared/conventions.md`。字段枚举见 `references/field-record-schema.yaml`。

## 定位

**Agent 做什么：** 扫描项目建立认知 → 接收信号 → 评估信息完整度 → 针对性提问 →
域判断与分流。

**实施人员做什么：** 提供现场材料（群聊、工单、口述）→ 回答 Agent 的针对性问题 →
确认条目内容。

**不做什么：** 完整 PRD/SRS/ADR、架构决策、技术选型、配置方案。

## 项目认知建立

intake 被触发时，Agent 先建立对项目的基线认知。这不是为了替实施人员做判断，
而是为了让自己具备"听懂现场语言"的能力。

扫描范围（按可用性）：

1. **代码模块结构**：主要目录、服务边界、模块划分。
2. **关键配置**：数据库、外部服务、部署环境。
3. **已有文档和决策记录**：ADR、PRD、会议纪要等。
4. **最近变更**：git log 近期 commit，了解活跃区域。

认知产出不是报告，而是内部上下文。当实施人员说"血压那个页面"时，Agent 应该知道
对应哪个模块、哪个服务、谁在维护——这样提问才能精准。

如果项目结构不清晰或无法扫描，在对话中说明"我对项目结构了解有限，可能需要你
多描述一些模块信息"，不要假装知道。

## 对话式工作流

### 阶段一：感知

收到材料后，快速感知：

- 这里大概有几件独立的事？
- 每件事的核心信号是什么（谁、在什么场景、遇到了什么、想要什么）？
- 哪些信息已经明确，哪些明显缺失？

感知结果用大白话告诉实施人员。例如：

> "这段对话里我看到两件事：一个是血压数据改不了、刷新会丢；另一个是字段顺序
> 想从'舒张压/收缩压'改成'收缩压/舒张压'。我先问你血压改不了这个问题——"

不要一次性输出完整表格或结构化记录。感知阶段的目的是**对齐理解**，让实施人员
有机会纠正 Agent 的解读。

### 阶段二：评估

对每件事评估信息完整度。一条完整的条目需要：

| 要素 | 说明 | 缺失时的表现 |
| --- | --- | --- |
| 角色 | 操作或受影响的人 | 不知道谁在用这个功能 |
| 模块 | 页面或能力名 | 不知道在哪个系统里 |
| 现象 | 可观察的现状 | 只知道"有问题"但不知道具体表现 |
| 诉求 | 期望结果 | 只知道有问题但不知道想要什么 |
| 证据等级 | 亲见/客户口述/推测 | 无法判断信息可信度 |
| 复现状态 | 已复现/未复现/无法复现（缺陷类） | 无法判断是否值得投入 |

评估是内部过程，不需要向用户展示评估表格。但评估结果决定下一步问什么。

### 阶段三：提问

针对缺口提问。提问原则：

1. **基于项目认知问精准问题。** 不要问"请提供模块名称"，而是问"这个血压页面是
   个人健康监测里的还是体检报告里的？"——因为 Agent 已经扫过项目，知道有几个
   候选答案。

2. **只问会改变条目拆分或模块归属的问题，不设数量上限。** 现场对话要压低
   实施人员的认知负荷：一次只问当前最关键的缺口，不要一次甩出一堆问题。

3. **用大白话，不用框架术语。** 不要问"这个现象的证据等级是什么"，而是问"这个
   情况是你自己看到的，还是客户告诉你的？"

4. **允许实施人员说"不知道"。** 如果实施人员也不清楚，标为"待确认"，不要逼迫
   或反复追问同一件事。

5. **逐条收敛。** 先搞定一件事，再聊下一件。不要同时推进多条条目的补全。

### 阶段四：收敛

当一条事项的信息足够时：

1. 形成条目：角色、模块、现象、诉求、类型（缺陷/体验/流程配置/待定）、主次。
2. 标注证据等级和复现状态（缺陷类）。
3. 用大白话向实施人员确认："我理解的是……对吗？"
4. 确认后，做 Cynefin 域判断（见下文"域判断与分流"）。

信息"足够"的标准不是所有字段都有值，而是**Agent 能判断这条该往哪里送**。
模块名可以是"待确认"，但 Agent 需要知道这是前端问题还是后端问题、是配置问题
还是代码问题——这些可以通过项目认知推断，不一定需要实施人员回答。

## 沟通原则

**用实施人员的语言描述思考过程。** 告诉用户"我看到了什么、怎么理解的、接下来
要搞清什么"，不暴露框架术语。

好的说法：
- "这段信息还不够判断是哪块的问题，你能告诉我……"
- "我先搞清血压改不了这个问题，然后再聊字段顺序。"
- "许宁宁说他看到了页面，这个信息很关键——"

不好的说法：
- "我现在处于 confused 域，正在执行 probing 策略。"
- "正在执行信息分层，将你的输入归类为 facts 和 assumptions。"
- "问题单状态保持为 intake，暂不做复杂度判断。"

**实时纠正优于事后审核。** 在对话过程中让实施人员纠正 Agent 的理解，比最后
输出一份完整记录让人审要高效得多。

## 现场记录模型

条目是原子交接单元。核心四元组：

- **角色**：操作或受影响的人。禁止填提出人姓名。
- **模块**：页面或能力名。对话未出现则写"待确认"，禁止编造菜单名。
- **现象**：可观察现状，不写根因。必须带证据等级（亲见/客户口述/推测）。
- **诉求**：期望结果。技术方案话不是诉求。

附加字段：

- **类型**：缺陷/体验/流程配置/待定——用于粗分流。
- **主次**：卡住业务的缺陷优先于顺带体验。
- **复现状态**：缺陷类必填（已复现/未复现/无法复现/不适用）。
- **提出人**：谁在群里提的。条目级字段，一次会话可能多人各提各的。
- **证据**：1-2 句原话，随提出人一起呈现。

拆条规则：

- 有现象无诉求 → 可建条，诉求标"待澄清"。
- 有诉求无现象 → 允许，现象写"无故障现象，属体验/顺序/配置问题"。
- 一条里两个无关诉求 → 必须拆条。
- 问题与诉求并存 → 拆条并用主次标记。

证据等级是门槛，不是标签：

- "推测"的条目不得标已确认。
- 缺陷类"未复现"时不得标已确认或交接，待确认里必须有复现问题。
- "无法复现"可关闭，但要记下试过的步骤。
- 客户说得再肯定，没人看过就是"客户口述"，不因语气升级。

## 域判断与分流

条目确认后，Agent 结合项目上下文做 Cynefin 分类（见 `../../shared/cynefin.md`）。

| 信号 | 域判断 | 去向 |
| --- | --- | --- |
| 类型为流程配置且模块明确 | 通常 `clear` 或 `complicated` | 配置侧处理，附一句下一步 |
| 类型为缺陷且需改接口/库表/服务逻辑 | 通常 `complicated` | 标"需研发" |
| 用户要先验证/选型/止损 | 由 `engineering-decision` 判断 | 转 `engineering-decision` |
| 用户只要正式 PRD/SRS/ADR | 由 `engineering-documents` 处理 | 转 `engineering-documents` |
| 需求未验证、依赖用户行为反馈 | 通常 `complex` | 建议实验或 MVP |
| 信息不足无法判断 | `confused` | 继续提问或标"待确认" |

交接时把条目标为"已交接"并回填去向（工单号、文档条目号或 decision_brief 标识）。
只是口头说"这个要研发"不算交接。

## 紧急伤害

若存在正在扩大的错误数据写入、重复扣费、权限放开、生产配置误改且仍在扩散：
先给止损提示（停哪个入口、找谁、先恢复什么），再回来整理现场记录。

## 反模式

- 首轮输出技术方案、根因长文或配置项清单冒充现场记录。
- 把"锁了"等猜测写成事实。
- 编造未出现的产品菜单名。
- 把提出人写进角色。
- 把提问、术语差异或信息缺失当成冲突。
- 未复现的缺陷标已确认或直接开研发工单。
- 无法复现就静默关闭，不记录试过的步骤。
- 为新增字段增加表格列，把输出撑宽。
- 一次性输出完整记录让人审，而不是对话式补全。
- 问"请提供更多信息"而不是基于项目认知问精准问题。
- 暴露框架术语（Cynefin、信息分层、状态机等）给实施人员。
