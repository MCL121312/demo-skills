# Implementation Intake

面向**实施人员**的现场澄清入口：把现场对话变成一份可协作的 **现场记录**
（角色 · 模块 · 现象 · 诉求 + 验证），而不是工程决策简报、正式规格，或过早的
「保留/去掉/同步」配置方案。

与 `engineering-decision` 并行，不互相替代。实施链路默认走本 Skill；只有实施方明确要求
做研发级判断（先验证还是先做、架构权衡、事故止损）时，再交给 `engineering-decision`。

字段枚举与拆条细则见 `references/field-record-schema.yaml`，边界不清时再读；
案例见 `EXAMPLES.md`。

## 输出语言与受众文案

默认简体中文。英文仅保留字段名、系统名、接口名和固定枚举。

面向实施人员时：

- 只写对方要落地的结论：摘要、条目四元组、提出人与证据、未知、验证、待确认问题；
  冲突仅在确有互斥断言时才出现。
- **判据是能否原样转发**：输出会被贴进客户群或工单，读的人不需要、也不应该知道
  本 Skill 的工作方式。需要升级时直接说「建议转研发决策」，不解释自己跳过了什么。

  错误示范：`该问题属于流程配置类，暂不做复杂度与域判断，记录状态保持草稿。`

  正确示范：`预约填过的信息，激活后又要求填一次。还需要确认三件事：……`
- 没有要求贴 YAML 时，用自然语言短段落 + 清单/表格，不要堆内部章节标题。
- 首轮禁止技术方案、根因长文、臆造菜单名或「建议改配置项 XXX」。

## 目标

1. 一条输入材料 → 一份 **现场记录** → 内含 1..N 条 **条目**。
2. 问题与诉求并存时 **拆条**，用主/次标记，不揉成一句模糊诉求。
3. 每条条目固定四元组：**角色 · 模块 · 现象 · 诉求**；附类型、证据、验证。
4. 人机协作：草稿 → 人确认拆并与字段 → 补全验证；按需再投影用户故事/用例。
5. 整单最多三个高影响确认问题。

## 边界

| 做 | 不做 |
| --- | --- |
| 群聊/工单 → 现场记录（条目拆分、证据、验证、待确认） | 完整 PRD/SRS/ADR/概要设计正文 |
| 标出谁该确认、缺什么才能定模块/拆条 | 研发级判断：复杂度评分、技术选型对比 |
| 粗分流：流程配置 / 需研发 / 转工程决策 | 未经确认就改生产配置或承诺已同步 |
| 人要求时投影用户故事或用例摘要 | 默认输出完整用户故事/UML 用例正文 |

用户只要「整理现场」时，停在现场记录。用户明确说「转研发写 PRD/设计」或「按工程决策走」时，
再交接，不要默认串文档工作流。

不默认把现场记录落盘；仅当用户要求「落盘/保存」时再写 markdown。

## 核心模型

- **现场记录**：整次现场会话的容器（标识、来源、摘要、状态、冲突、未知、待确认、条目列表）。
  标识格式 `IN-YYYYMMDD-NN`，条目标识为记录标识加 `#序号`，用于跨会话和跨工单追溯；
  聊天里仍可简称「条目2」。序号不复用，作废的条目标「已关闭」。
- **条目**：原子可交接单元。四元组关系：
  - 有现象无诉求 → 可建条，诉求标「待澄清」，追问期望结果。
  - 有诉求无现象 → 允许；现象写「无故障现象，属体验/顺序/配置问题」。
  - 一条里两个无关诉求 → **必须拆条**。
- **现象**只写可观察现状，不写根因；**诉求**只写期望结果，技术方案话不是诉求。
- **现象必须带证据等级**（`亲见` / `客户口述` / `推测`），缺陷类还要带**复现状态**
  （`已复现` / `未复现` / `无法复现`）。这是本框架「不允许把推断写成事实」在实施链
  的落法：现场报告默认是待验证的声称，没人看过就是客户口述，客户说得再肯定也不升级。
- **模块**对话未出现则写「待确认」，禁止编造产品菜单名。
- **角色**是操作或受影响的人，**提出人**是谁在群里提；两者不同时都要写，
  禁止把提出人填进角色。提出人是条目级字段，一次会话可能多人各提各的。
- **证据等级和复现状态是门槛，不是标签**：等级为`推测`的条目不得标已确认；
  缺陷类`未复现`时既不能标已确认也不能交接，且待确认里必须有一个复现问题
  （谁、什么条件、哪个单号）；`无法复现`可以关闭，但要记下试过的步骤，业务坚持
  存在就保留待确认或转研发查日志，不许静默关掉。放行未复现的报告，等于把传闻
  变成研发工单，而且「改好了」根本没法验收——本来就没人见过它坏。
- **状态是条目级的**（`待确认` / `已确认` / `已交接` / `已关闭`），逐条流转，
  不跟随记录状态；一条已拍板、另一条还在澄清是常态。交接到工单、研发或下游
  文档时，必须把状态改为「已交接」并回填**去向**（工单号、文档条目号或
  `decision_brief`），否则下游产物找不回源头。
- **冲突**只收「两方对同一事实给出互斥断言，且双方都是陈述句」，例如
  「功能锁住了」对「没有锁」。提问、术语口径不同、信息缺失都进未知或待确认。
  一条信息只落一个区；已经写成待确认问题的，冲突区不再重复。没有互斥断言时
  整项省略。
- 用户故事 / 用例是确认后的 **投影视图**，源数据仍是条目，避免两套真相。

## 工作流程

### 0. 紧急伤害

若存在正在扩大的错误数据写入、重复扣费、权限放开、生产配置误改且仍在扩散：先止损提示
（停哪个入口、找谁、先恢复什么），再回来写现场记录。不要在伤害扩大时继续访谈细节。

### 1. 首轮：现场记录草稿

从材料抽出：

1. 来源与一句话摘要（中性，不写方案）。
2. 条目列表：每条含角色、模块、现象、诉求、类型（`缺陷` / `体验` / `流程配置` / `待定`）、主次、提出人与证据；验证可先写草案或「待补全」。
3. 冲突（仅在有互斥断言时）、未知。
4. ≤3 个待确认问题（只问会改变拆条或模块归属的）。

状态标为 `待确认`（或内部等价的草稿）。本轮不要输出变更方案或根因分析。

### 2. 确认轮：等人改

等人确认：改角色/模块、拆并条目、定主次。人未确认前不要当作已定需求推进配置或研发承诺。
逐条把状态从「待确认」改为「已确认」，不要整份记录一次性翻状态。

### 3. 补全轮：验证与可选投影

按已确认条目补全 **验证**（操作 → 观察；失败时应看到什么；同步类未证则标「待证实」）。

仅当人要求「写成用户故事 / 用例」时再投影：

- 用户故事：`作为【角色】，希望【诉求】，以便【从现象推导的价值】`；验收条件 = 验证步骤。
- 用例摘要：参与者=角色，范围=模块，主成功场景由验证改写，异常场景来自现象。

### 4. 分流

| 信号 | 去向 |
| --- | --- |
| 类型为 `流程配置` 且模块明确 | 可附一句「配置侧下一步」；不展开选型 |
| 类型为 `缺陷` 或需改接口/库表/服务逻辑 | 标「需研发」 |
| 用户要先验证/选型/止损 | `engineering-decision` |
| 用户只要正式 PRD/SRS/ADR | `engineering-documents`（缺上下文时先本 Skill 出已确认现场记录） |

交接时（无论去工单、研发还是下游文档）把该条目标为「已交接」并回填去向。

## 输出协议

### 首轮（默认）

须覆盖：

1. **摘要**：一句话；记录标识写在标题行。
2. **条目**：表格或清单，每条含编号、角色、模块、现象、诉求、类型与主次。
   **表格最多六列**，字段增加不等于输出变重：提出人与证据合并成表格下方一行
   `#1 · 提出人 X（时间）：「原话」`；证据等级与复现状态以括号后缀写进现象格，
   如「修改后刷新数值恢复（客户口述·未复现）」；首轮状态统一为「待确认」时整项
   不渲染；去向仅在已交接时出现；置信度和验证草案不进首轮表格。
3. **冲突 / 未知**（有才写）。
4. **待确认**：0–3 个问题。

同一条信息不要在冲突、未知、待确认里各写一遍；重复即视为输出缺陷。

可选短附录（用户要转发群里时再用）：

```text
【现场记录 IN-YYYYMMDD-NN】
摘要：
#1 角色 / 模块 / 现象 / 诉求（主·缺陷）｜提出人：
#2 …
冲突：（无互斥断言就删掉这行）
待确认：
```

### 补全轮与投影

人确认后补验证；人点名要故事/用例时再输出投影，并声明源条目编号。

## 完成前检查

- 未把推断写成「系统已经会同步」或已定性根因。
- 未默认输出工程决策或正式规格全文。
- 问题与诉求并存时已拆条，主次已标。
- 模块未知时为「待确认」，未编造菜单名；角色写的是操作/受影响的人，提出人单独成项。
- 首轮未输出技术方案或配置项清单冒充诉求。
- 冲突区只有互斥断言，没有把提问或术语差异算成冲突，也没有与待确认重复；
  待确认问题 ≤ 3，且每个都能改变拆条或模块归属。
- 有「去掉重复填写」类诉求时，验证含同步检查，未证实则标「待证实」。
- 每条现象带证据等级，缺陷类带复现状态；未复现的缺陷未被标已确认或交接，
  且待确认里有复现问题。
- 记录有标识、条目有编号且编号未复用；已交接的条目回填了去向。
- 表格未超过六列，新增字段没有把首轮输出撑宽。
