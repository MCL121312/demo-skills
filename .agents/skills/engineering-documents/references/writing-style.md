# 正文的写法（人读产物）

**正文**指 `<slug>.md` 这份人读产物；**约束文件**指 `<slug>.constraints.yaml`。本文件只约束正文。

判断标准只有一条：**读者读完能做决定**。读起来舒服是手段，不是目的；但读起来别扭通常意味着有人做不了决定。

## 四条要求

1. **作者在场。** 每个方案段落末尾要给立场与前提：「倾向 A，因为 B；如果 B 不成立就要改成 C」。有担心就写出来（「这里我还没想清楚」），不要把不确定写成规则。
2. **密度有疏落。** 重要的铺开、边角的带过。全文只保留真正需要对照的表（一般 2–3 张），其余写成段落。
3. **人称稳定。** 以系统或仓库为主语：「本服务不做 X」「`report.service` 负责检中文书」。不要在同一篇里混用「我们 / 本方案 / 本文 / 手机不必」。
4. **断言挂源。** 非平凡结论后加 `[源: 文件#章节]`，查不到来源的写 `[未核实]`。能被机器判定的数值不进正文，交给约束文件。

## 三类对话遗迹（禁止出现在正文）

**对话遗迹**：起草过程中产生的、只对起草者或执行者有意义，对读者无意义的句子。

生成稿件最常见的「怪」来自把对话里的东西印进了文档。逐条禁掉：

| 遗迹 | 长什么样 | 去哪 |
| --- | --- | --- |
| 自指元注释 | 「名称说明：…」「本文只规定…」「（E15 已并入 E14。）」「本方案第一阶段…」 | 删；需要留痕进提交信息 |
| 改稿便条 | 「（此处待补）」「（已并入 X）」 | 删 |
| 对执行者的指令句 | 「实现时以 X 为准」「手机不必实现本节」「不得塞进 requiredCodes」「见 FR-14.4.5」 | 进约束文件；正文只留必要的一句「以 X 为准」或直接不提 |

## AI 味自查

| 症状 | 改法 |
| --- | --- |
| 每节质地一样，全是「结论 + 表格 + 一句解释」 | 按重要性重排，删掉一半的表 |
| 开头 TL;DR，正文再复述一遍 | 二选一 |
| 对称句式与三段排比（「不是 X，而是 Y」「一来…二来…」） | 改成一个具体例子 |
| 编号脚手架先于叙述（一节里出现 5 个以上 ID） | 正文用名字，ID 留在约束文件 |
| 数字精确却无出处 | 挂源，或改成约束文件里的引用 |
| 把禁令当正文写（「不得」「禁止」「必须」） | 移入约束文件；正文只写「因此会怎样」 |

## 用词与自造词

优先使用已经存在的名字，其次才允许造词。

| 类别 | 规则 |
| --- | --- |
| 已有词（代码 / 接口 / Schema / 上游规范 / 行业标准里已存在） | 直接沿用，禁止改名，禁止缩写化；首次出现附原文与出处 |
| 必须造的词（概念确实存在，但没有现成名字） | 允许，但三条缺一不可：一句话定义、边界（什么**不**属于它）、全篇唯一写法 |
| 禁造 | 自造分级（一档 / 二档 / 三阶）、自造流程名（送审态 / 闭环态）、隐喻替代、自造三字母缩写 |

1. **一名一概念，一概念一名。** 同一概念全篇只用一个词，同一个词只指一件事。禁止同义轮换（「电脑端 / Host / 桌面端」指同一个东西）。
2. **可检索优先。** 正文里的名词应当能在仓库或规范里 grep 到。检索不到就必须进术语表。
3. **能替换成大白话。** 一个词换成朴素描述后信息不减少，它就是空的，删掉。
4. **术语表带映射列。** 两列：文档里的词 → 代码 / 规范里的名字 + 出处。填不出第二列的词就是自造词，删掉或补定义与出处。术语表少于 3 条就不设这一节。

机器通道（约束文件、枚举、Schema）允许造词，但必须集中定义一次，正文不得引用机器词（见 `layering.md`）。

## 一秒钟判别法

把正文里所有「对执行者说的话」和「作者给自己的便条」划掉，再读一遍。如果更通顺，那些就是别扭的全部来源。
